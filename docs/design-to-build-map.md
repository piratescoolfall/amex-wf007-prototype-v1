# Design-to-build mapping — seven controls

This mapping documents the Product Owner-supplied classroom simulation design for future implementation in React, JavaScript, and Vite. It does not implement application code. The WP-04A source is not present in the repository, so the numbered controls below are local documentation labels, not WP-04A requirement IDs. No classroom rule is presented as an actual American Express policy.

| Local control | Design and planned implementation boundary | Planned acceptance checks and evidence |
| --- | --- | --- |
| 1. Synthetic simulation boundary | Use fictional customers, cases, transactions, and simulated CSR/Supervisor roles. Clearly identify the classroom prototype and all mocked AI/action results. No real banking/payment connections, credentials, secrets, or paid services. | Inspect fixtures and displayed labels; confirm fictional $500 scenario and simulated roles. Review dependencies and network behavior for absence of real financial integrations. Preserve review notes and screenshots. Simulated roles do not prove production authentication or authorization. |
| 2. Mandatory human CSR verification | Only an authorized human in the simulated CSR role may attest completion of the approved simulation verification steps. Gate assessment, manual fallback, and AI processing on this attestation; enforce the gate in workflow logic as well as the UI. Record attestation without verification secrets. | Before attestation, attempt assessment, manual assessment, and AI processing: each is blocked and audited. Attempt attestation as Supervisor or without CSR authority: blocked. After CSR attestation, assessment is available. Inspect audit payloads for absence of secrets. Preserve results for UI and direct workflow attempts. |
| 3. Bounded deterministic simulated AI and fallback | Use reproducible synthetic AI outcomes: usable, usable but uncertain, unusable, and failed. Label output **Simulated AI**. Show usable but uncertain output with a visible warning requiring human review. Use manual fallback for failed or unusable output, retaining all gates. AI may summarize, classify, identify uncertainty, and draft recommendations only. | Repeat the same fixture and confirm deterministic output. Confirm uncertain usable output stays visible with warning. Confirm failed/unusable outcomes offer manual fallback without bypassing verification. Attempt to have AI attest verification, approve, reverse, or close: no such authority or transition. Preserve output snapshots and audit events. |
| 4. Human Supervisor approval for fictional $500 reversal | Require a human in the simulated Supervisor role to approve the fictional $500 reversal. Escalation and recommendations grant no approval. When authorization is missing, block the action and display the exact message below. Rejection and withdrawal keep the case open for review. | Attempt reversal without authorization, including after escalation and an AI recommendation: blocked, exact message displayed, no mock action. Attempt approval as CSR: blocked. Supervisor approval records a decision but executes no reversal. Reject or withdraw: case remains open; no reversal or closure. Preserve decision and blocked-action evidence. |
| 5. Separate CSR-triggered mock reversal | Recorded Supervisor approval enables a distinct explicit human CSR action. Recheck CSR authority, verification, and approval at execution. Execute only the mock reversal; distinguish the simulated action from approval and recommendation. Failed actions leave the case open for review. | Approval alone produces no reversal. An authorized CSR trigger with all gates satisfied produces a simulated result. Direct execution attempts with any missing prerequisite are blocked. Missing Supervisor authorization uses the exact message below. Inject mock failure: log failure and retain open status. Preserve separate approval, trigger, and result events. |
| 6. Explicit human CSR closure | Only an authorized human CSR may explicitly confirm simulated closure after the successful approved mock-action path. No automatic closure on AI output, escalation, approval, or reversal success. Rejected, withdrawn, and failed-action cases remain open for review. | Confirm each intermediate event leaves the case open. Confirm successful mock reversal alone leaves it open. CSR confirmation on the eligible path closes it; Supervisor/AI closure attempts are blocked. Attempt closure on rejected, withdrawn, and failed-action paths: blocked and audited. Preserve transition evidence. |
| 7. Synthetic audit and JSON export | Record synthetic case ID, verification attestation, blocked actions, simulated AI output and uncertainty, human decisions, simulated action results, and case transitions. Preserve the distinction between recommendation, approval, and simulated execution. Export these events as JSON without verification secrets; export must not mutate case state. | Run successful, uncertain, fallback, missing-authorization, rejected, withdrawn, and failed-action scenarios. Parse each exported JSON file; verify required event content and case association, absence of secrets, and distinct decision/action/closure records. Confirm export leaves case state unchanged. Preserve representative synthetic exports and results. |

Exact missing-authorization message (display without surrounding quotation marks):

> Supervisor assistance is needed for this action. No approval or account change has been performed.

## Validation status and limits

Pre-commit documentation validation: both Mermaid diagrams passed the installed Mermaid flowchart and sequence grammar parsers, with semantic callbacks stubbed to avoid browser rendering dependencies. Visual rendering was not tested. Manual workflow review confirmed the verification gate, uncertain-output warning, manual fallback, exact missing-authorization message, separate Supervisor approval and CSR mock action, explicit CSR closure, open review outcomes, and JSON audit export. The mapping contains seven numbered controls. Repository review confirmed only these three Markdown files were added, with no application code or dependencies added.

Acceptance checks in this mapping are planned checks, not executed application tests. This documentation change provides no runtime, authorization, AI, or audit-security validation. Future implementation must preserve evidence of important tests and limitations in small, testable increments, after Product Owner review and approval of an implementation plan as required by `AGENTS.md`.

Further treatment of rejected, withdrawn, or failed-action cases is not specified here: they remain open for review. Any additional disposition workflow requires an approved design decision. JSON export is an evidence artifact for the classroom simulation; no production durability or tamper resistance is claimed.

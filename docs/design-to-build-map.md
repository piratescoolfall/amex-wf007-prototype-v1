# Design-to-build mapping — seven controls

This mapping documents the Product Owner-supplied classroom simulation design for future implementation in React, JavaScript, and Vite. It does not implement application code. The WP-04A source is not present in the repository, so the numbered controls below are local documentation labels, not WP-04A requirement IDs. No classroom rule is presented as an actual American Express policy.

| Local control | Design and planned implementation boundary | Planned acceptance checks and evidence |
| --- | --- | --- |
| 1. Synthetic simulation boundary | Use fictional customers, cases, transactions, and simulated CSR/Supervisor roles. Clearly identify the classroom prototype and all mocked AI/action results. No real banking/payment connections, credentials, secrets, or paid services. | Inspect fixtures and displayed labels; confirm fictional $500 scenario and simulated roles. Review dependencies and network behavior for absence of real financial integrations. Preserve review notes and screenshots. Simulated roles do not prove production authentication or authorization. |
| 2. Mandatory human CSR verification | Only an authorized human in the simulated CSR role may attest completion of the approved simulation verification steps. Gate assessment, manual fallback, and AI processing on this attestation; enforce the gate in workflow logic as well as the UI. Record attestation without verification secrets. | Before attestation, attempt assessment, manual assessment, and AI processing: each is blocked and audited. Attempt attestation as Supervisor or without CSR authority: blocked. After CSR attestation, assessment is available. Inspect audit payloads for absence of secrets. Preserve results for UI and direct workflow attempts. |
| 3. Bounded deterministic simulated AI and fallback | Use reproducible synthetic AI outcomes: usable, usable but uncertain, unusable, and failed. Label output **Simulated AI**. AI may summarize, classify, identify uncertainty, and draft recommendations only. | Repeat the same fixture and confirm deterministic output. Confirm uncertain usable output stays visible with warning. Confirm failed/unusable outcomes offer manual fallback without bypassing verification. | 4. Human Supervisor approval for fictional $500 reversal | Require a human in the simulated Supervisor role to approve the fictional $500 reversal. Escalation and recommendations grant no approval. | 6. Explicit human CSR closure | Only an authorized human CSR may explicitly confirm simulated closure after the successful approved mock-action path. No automatic closure on AI output, escalation, approval, or reversal success. Rejected cases remain open until an eligible explicit cancellation; failed-action cases remain open. | Confirm each intermediate event leaves the case open. Confirm successful mock reversal alone leaves it open. CSR confirmation on the eligible path closes it; Supervisor/AI closure attempts are blocked. Attempt closure on rejected and failed-action paths: blocked and audited. Preserve transition evidence. |
| 7. Synthetic audit and JSON export | Record synthetic case ID, verification attestation, blocked actions, simulated AI output and uncertainty, human decisions, simulated action results, and case transitions. Export these events as JSON without verification secrets; export must not mutate case state. | Run successful, uncertain, fallback, missing-authorization, rejected, cancelled, and failed-action scenarios. Parse each exported JSON file; verify required event content and case association, absence of secrets, and distinct decision/action/closure records. Confirm export leaves case state unchanged. Preserve representative synthetic exports and results. |

## Validation status and limits

Pre-commit documentation validation: both Mermaid diagrams passed the installed Mermaid flowchart and sequence grammar parsers, with semantic callbacks stubbed to avoid browser rendering dependencies. Visual rendering was not tested. Manual workflow review confirmed the verification gate, uncertain-output warning, manual fallback, exact missing-authorization message, separate Supervisor approval and CSR mock action, explicit CSR closure, open review outcomes, and JSON audit export. The mapping contains seven numbered controls. Repository review confirmed only these three Markdown files were added, with no application code or dependencies added.

Acceptance checks in this mapping are planned checks, not executed application tests. This documentation change provides no runtime, authorization, AI, or audit-security validation. Future implementation must preserve evidence of important tests and limitations in small, testable increments, after Product Owner review and approval of an implementation plan as required by `AGENTS.md`.

The Product Owner approved cancellation on 2026-10-09, replacing withdrawal. All open case types may be cancelled by CSR with current verification and available evidence before any processed reversal, including rejected requests. No assessment or Supervisor approval is required for cancellation. A preset reason and strict explicit human confirmation are mandatory. Cancellation revokes current approval and closes the case as Closed — Cancelled. Success and failure action results both block cancellation and require Supervisor review to determine whether a separate corrective action is appropriate. No corrective-action implementation or automatic undo is authorized. JSON export is an evidence artifact for the classroom simulation; no production durability or tamper resistance is claimed.


## Approved cancellation disposition

The Close / Cancel Case control requires one of Customer no longer wishes to proceed, Duplicate case opened in error, or Request no longer required. Cancellation logs the CSR decision, reason, timestamp, closure confirmation, and transition; JSON includes cancellationReason and closureOutcome: cancelled. Closed cases block further AI/manual assessment, Supervisor decisions, reversal processing, material edits, and duplicate closure. The former withdraw action is unavailable. Incomplete-verification closure and successful-resolution closure remain distinct, with their existing safeguards.

Acceptance checks cover all case types and pre-action stages, rejected cases, missing/stale verification, unavailable evidence, wrong role, missing/invalid reason, nonboolean confirmation, success/failure action results, duplicate closure, immutable original AI audit snapshots, refreshed communication status, and JSON export without state mutation. Cancellation never approves or performs a financial action. See the cancellation section in test-evidence.md for executed results.


## Approved conditional routing and routine completion — AMX-routing-1

Product Owner approved the conditional-routing plan. The shared versioned configuration in approvalRouting.js governs workflow guards, navigation, approval labels, reports, and export. These are project rules, not official American Express policy. No additional monetary threshold is introduced.

| Matched rule | Route | Authorized path |
| --- | --- | --- |
| routine-information | CSR | Statement explanation request or transaction inquiry with Information request category and explicit false exception attributes: verification, reviewed assessment, explicit CSR completion, separate CSR closure. No financial action. |
| reversal-500 | Supervisor | Exact Reversal request type/category and $500.00 amount: verification, reviewed assessment, escalation, current Supervisor approval, separate CSR training reversal, explicit closure. |
| case-exception | Hold for human review | Account-change request or evidence conflict: verification and human assessment required before requesting review. No financial approval, execution, or routine completion is authorized. |
| missing-attributes / unsupported-request / unsupported-reversal / invalid-policy | Hold for human review | Missing/malformed authority attributes, unknown type/category, other reversal amount or invalid configuration: no processing authority. |

Exception checks precede routine matching. A displayed amount on an information request does not confer financial authority. A routing decision is not identity verification, a human assessment, approval, action, or closure. Missing verification or evidence still blocks processing. More Information Required for holds identifies a routing/evidence need, not a recorded Supervisor decision. Closed cancellation/incomplete paths retain Not Required; cancellation and incomplete verification remain their separate approved dispositions.

Routine completion records csr_request_completed with case revision, rule ID, policy version, request type and human CSR actor; it keeps the case open. Separate human confirmation closes it as Successfully Resolved. Closure after a routine request never claims a reversal. Completion and Supervisor approval bind the policy version, rule ID and revision. All new audit events include evaluated routing metadata (version, rule, route, reason, revision); creation and exports include it too. Material exception changes re-evaluate routing and invalidate previous authority. Unknown routes fail closed. No normal dashboard rule editor or security scenario controls are introduced.

Acceptance checks cover independently resolving both routine types and newly created requests, mandatory $500 approval, unsupported/mismatched cases, exceptions, stale authority/policy version, missing verification/evidence, no financial action for routine cases, guarded review navigation, separate human completion/closure, immutable AI snapshots, routing JSON evidence, and all existing cancellation/failure/security paths. See the corresponding test evidence section for executed results.

### Supervisor approval requirement presentation

Supervisor Review labels the $500 reversal “Supervisor Approval Required” and explains that submitting a request for review does not authorize processing. The $500 requirement remains an application-defined, Product Owner-approved rule, not an official American Express policy. Display formatting removes “project-specific” from routine routing descriptions without rewriting stored audit/export evidence or changing approval routing. Review submission, human Supervisor approval and CSR reversal processing remain separate guarded actions.
